# 6차 — 구축 및 검수

진행 순서는 `MVP 범위 구축 → 검수 및 안정화 → 배포(CI/CD) → 추가 구축`으로 고정한다.

## 1. MVP 범위 구축

### MVP 목표

신규 상담이 들어온 시점부터 담당자가 첫 연락을 완료하고 다음 행동을 등록할 때까지 영업 건이 조용히 방치되지 않게 한다.

최우선 완료 기준은 **유효 신규 상담의 1영업일 이내 첫 연락 완료율 100%를 시스템에서 측정할 수 있는 것**이다.

### MVP 포함

1. Google Workspace 로그인과 관리자·열람자 권한
2. Emergent 신규 문의 수신과 원본 ID 기반 중복 방지
3. 수동 영업 건 등록
4. 회사·영업 건·담당자 저장과 조회
5. 대한민국 주말·공휴일을 반영한 첫 연락 기한 계산
6. 상담 대상 제외와 사유 기록
7. 첫 연락 완료 기록: 통화 성공 또는 통화 실패 후 문자 발송
8. 다음 행동 등록·완료·지연 표시
9. 담당자 위임과 휴가 중 신규 문의 자동 위임
10. 오전 9시 업무 알림과 오후 3시 기한 초과 반복 알림
11. 전체 변경 이력과 쓰기 요청 중복 방지
12. 모바일 `할 일·영업판·영업 상세·직접 추가` 화면의 실제 API 연결

### 추가 구축으로 연기

- 계약·서비스별 계약 금액
- 청구 일정·계산서·입금·취소·환불
- 월간 성과와 가중 예상 수주
- AI 서비스 계정과 재무 승인
- Google Drive 문서 연결 고도화
- 범용 장애 Webhook과 관리 화면의 전체 운영 기능

프레임 화면은 유지하되 연기된 영역에는 실제 저장 기능을 연결하지 않는다.

### MVP 수직 구축 순서

1. 공유 계약과 PostgreSQL 스키마
2. 신규 영업 건 등록·목록·상세 API
3. 1영업일 기한 계산과 첫 연락 완료 API
4. Web 핵심 화면의 API 연결
5. Emergent HMAC Webhook과 5분 누락 복구
6. Google 로그인·권한
7. 다음 행동·위임·휴가
8. 이메일 알림 Worker·Cron

### API·데이터 기반 1차 구축

- `packages/contracts`: Zod 기반 요청·응답 계약
- `apps/api`: NestJS REST API와 OpenAPI
- `apps/api/src/db/migrations`: PostgreSQL 버전 마이그레이션
- `POST /api/v1/deals`: 신규 문의 등록
- `GET /api/v1/deals`: 커서 목록
- `GET /api/v1/deals/:id`: 상세 조회
- `POST /api/v1/deals/:id/first-contact`: 첫 연락과 다음 행동 기록
- 모든 쓰기 요청에 `Idempotency-Key` 요구
- Emergent 원본 ID 중복 방지
- 회사명 정규화 기반 회사 연결
- 생성·첫 연락 변경 감사 로그 보존
- 개발 환경 메모리 저장소, 운영 환경 PostgreSQL 강제

## 2. 검수 및 안정화

MVP 기능 완료 후 다음 게이트를 통과해야 한다.

- 업무 규칙 단위 테스트
- API 계약·오류 응답·중복 실행 테스트
- Web 핵심 사용자 흐름 E2E
- 모바일 360·412·430px 가로 넘침 검사
- 키보드·포커스·명암비 검사
- 외부 연동 실패·인증 만료·재시도 검사
- PostgreSQL 백업·복원 리허설
- 운영 데이터 없이 스테이징 시나리오 검수

### 2026-08-19 1차 구축 검수 결과

- 신규 영업 건 직접 등록 → 상세 조회 → 첫 연락 완료 → `초기 상담·고객 응답 대기` 갱신 통과
- 업무 규칙·API·Web 단위 테스트 10건 통과
- 실제 API 연결 Playwright 시나리오를 포함한 E2E 14건 통과
- 전체 46개 프레임의 모바일 가로 넘침 회귀검사 통과
- lint, typecheck, Web 77페이지·API 프로덕션 빌드 통과
- PostgreSQL 실연동 검사는 GitHub Actions의 PostgreSQL 16 서비스에서 매 PR마다 실행하도록 구성

### 1차 사용자 검수 안정화

- `고객과 통화함`은 `초기 상담 · 초기 상담 완료`, `통화 실패 후 문자를 남김`은 `초기 상담 · 고객 응답 대기`로 전환한다.
- 첫 연락 저장 전에 선택 결과에 따른 변경 상태를 화면에서 미리 보여준다.
- 실제 영업 건의 다음 행동 카드에서 동작 없는 목업 `완료` 버튼을 제거했다.
- 첫 연락 전에는 `첫 연락 기록` 링크를, 완료 후에는 실제 저장된 다음 행동과 `예정` 상태만 표시한다.

### staging 배포 후 안정화

- 실제 UUID 영업 건의 `연락 기록`·`위임` 등 하위 작업 화면을 항상 동적 렌더링하도록 고정했다.
- 목업 경로의 정적 생성과 실데이터 API 조회가 섞여 발생하던 Next.js `static-to-dynamic` 500 오류를 제거했다.
- CI의 Playwright Web 서버를 `next dev`가 아닌 빌드 결과물의 `next start`로 실행하도록 변경했다.
- 운영 모드에서 영업 건 등록 → 연락 기록 → 첫 연락 완료를 포함한 E2E 14건을 다시 통과했다.

아직 MVP 완료로 표시하지 않는다. Emergent, 인증·권한, 위임·휴가, 알림 Worker·Cron은 후속 구축 대상이다.

## 3. 배포(CI/CD)

- GitHub Actions는 계정 Billing 제한으로 실행할 수 없어 자동 배포 경로에서 제외
- 로컬: lint, typecheck, unit, API integration, Web E2E, build
- `develop`: 검증 후 Railway 스테이징 수동 배포
- `main`: PR 확인 병합 후 Railway GitHub 소스로 운영 자동 배포
- DB 마이그레이션 성공 후 애플리케이션 배포
- `/api/v1/health` 상태 점검 실패 시 배포 실패 처리
- Web·API·Worker·Cron을 Railway 독립 서비스로 배포

운영 전용 PostgreSQL·API·Web 자원과 환경 변수·도메인을 준비했다. 사용자 승인에 따라 인증 전 임시 운영 배포를 실행했으며 실제 고객 데이터는 입력하지 않는다. 현재 실행 절차는 `docs/07-deployment-runbook.md`에 기록한다. Worker·Cron은 실행 코드가 생기는 후속 MVP 묶음에서 독립 서비스로 추가한다.

### 2026-08-19 production 인프라 준비 결과

- production 전용 PostgreSQL 18과 50GB 영구 볼륨 준비
- API·Web 설정 파일, 내부 DB 참조, 운영 도메인 준비
- API·Web Railway CLI 임시 운영 배포 및 상태 점검 통과
- lint, typecheck, 단위 테스트 11건, 프로덕션 빌드 77페이지 통과
- GitHub Actions 자동 트리거 중지 및 Railway CLI 승인형 배포 실행서 반영
- 운영 DB 0건 확인
- 예약 백업 활성화와 인증·권한 구현은 정식 운영 전환 게이트로 유지
- production API·Web을 `soonseek/tnc-crm`의 `main`에 직접 연결하고 병합 커밋 기준 배포 성공

## 4. 추가 구축

MVP 운영 결과와 실제 누락 유형을 확인한 뒤 계약·청구·성과·AI 자동화를 순차적으로 연결한다. 추가 구축 우선순위는 사용 빈도, 누락 위험, 재무 영향으로 결정한다.
